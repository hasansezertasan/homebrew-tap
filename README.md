# homebrew-tap

Homebrew tap for Hasan Sezer Taşan's Python command-line tools and macOS applications.

## Setup

1. In **Settings → Actions → General**, leave the default workflow permissions
   **read-only** and tick *Allow GitHub Actions to create and approve pull
   requests*. Every workflow here declares the write scopes it needs, so a
   read-only default keeps a future workflow that forgets to from inheriting
   them.
2. Run `mise install`, then add a formula or cask (see [Add a package](#add-a-package)).
3. Run `mise run generate-readme` and commit the generated package table with
   the new Ruby file.
4. Run `mise run check` before opening a pull request.

No owner or repository substitutions are required in the workflows. They derive
the tap name from the GitHub Actions context at runtime.

## Install packages

```sh
brew install hasansezertasan/tap/<formula>
brew install --cask hasansezertasan/tap/<cask>
```

Alternatively, tap the repository first:

```sh
brew tap hasansezertasan/tap
brew install <formula>
```

## Agent skills

Skills for operating the tap (scaffolding formulae and casks, and the checks a
generated field needs) come from
[`homebrew-tap-skills`](https://github.com/hasansezertasan/homebrew-tap-skills),
which this repository does not ship.

## Add a package

Formulae and casks are scaffolded by the `homebrew-add` skill from
[`homebrew-tap-skills`](https://github.com/hasansezertasan/homebrew-tap-skills),
which this repository does not ship. That repository is a skills repository
(`skills/<name>/SKILL.md`) that also installs as a Claude Code or Codex plugin.
Install it for your agent and ask it to add
a package; the skill documents the routes and options (PyPI formulae, GitHub
release casks), and which generated fields are guesses that need a human check.
Review inferred descriptions, homepages, dependencies, install and test blocks
(formulae), and app artifacts and zap stanzas (casks) before committing.
Do not write a formula or cask by hand and do not use `brew create`.

## Validate changes

```sh
mise run check      # tests, catalog freshness, YAML/Actions lint, Cobo
mise run lint       # every prek hook, across the whole repository
mise run style      # yamlfmt, yamllint, actionlint, action-validator, zizmor
brew test-bot --only-tap-syntax
```

`prek.toml` is the commit-time gate — `mise run hooks` installs it. It covers
file hygiene, `typos`, `markdownlint-cli2`, and the same YAML and Actions
toolchain `mise run style` runs without a hook install; the overlap is
deliberate so neither path is required.

For a formula, also run `brew audit --strict --online hasansezertasan/tap/<name>`, install
from source, and run `brew test`. For a cask, run
`brew audit --cask --strict --online hasansezertasan/tap/<name>`.

## Automated updates

Two weekly workflows use `brew livecheck` to find and propose formula and cask
updates. A formula bump is audited, built from source, and tested inside the run
that opens the pull request, because a pull request opened with `GITHUB_TOKEN`
does not trigger `tests.yml` — so `brew audit` alone would let a dependency that
fails to build reach a PR looking verified. Bottles still come from `tests.yml`
(see [Automated pull requests](#automated-pull-requests)). Two
`repository_dispatch` workflows let a package repository request an update
immediately after publishing:

- `update-formula` payload: `{"formula":"name","version":"1.2.3"}`
- `update-cask` payload: `{"cask":"name","version":"1.2.3"}`

The version is optional; the tap uses livecheck when it is omitted. A producer
repository needs a fine-grained token scoped to this tap with **Contents: write**
to call GitHub's repository dispatch API. Store it in the producer repository,
not in the tap.

Bottle publishing follows Homebrew's `brew test-bot` workflow: after CI builds
and uploads bottles, apply the `pr-pull` label to invoke `publish.yml`.

`zizmor.yml` audits the tap's own workflows on every push and pull request and
uploads findings to the Security tab. The dispatch receivers act on
attacker-controllable payloads with a write token, so keep it green.
`gitignore-drift.yml` re-renders the Cobo-managed `.gitignore` weekly and opens
a pull request when upstream boilerplate drifted. It opens its pull request the same way
the update workflows do.

### Automated pull requests

The update and drift workflows open their pull requests with the repository
secret `WORKFLOW_TOKEN` if defined, falling back to `GITHUB_TOKEN`. Because
GitHub does not start workflows for actions performed by `GITHUB_TOKEN`, a pull
request opened with it does not run `tests.yml` (the bottle build) or the other
checks. Run the `brew test-bot` workflow manually via `workflow_dispatch` on the update
branch before merging (tap-syntax and cask audit; the bottle build runs once
pull request checks start), or push to its branch, or configure a fine-grained
personal access token or GitHub App token for
this repository as `WORKFLOW_TOKEN` (**Contents: write** and **Pull requests:
write**) so the checks start automatically. The secret is optional.

## Pull request conventions

`check-pr-title.yml` requires
[Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/) titles
and `check-branch-name.yml` requires
[Conventional Branch](https://conventional-branch.github.io/) names, both
reported as a sticky comment on the pull request. `renovate/*` and the
`auto-update/*` branches the bump workflows push are exempt.

## Managed boilerplate

`.gitignore` is generated from GitHub's macOS, Windows, Linux, Visual Studio Code,
Python, and Ruby templates with [Cobo](https://github.com/hasansezertasan/cobo).
Its exact inputs are recorded in `cobo.lock`.

```sh
cobo check --strict
cobo sync
```

Do not edit the generated blocks by hand; update their Cobo inputs and re-render
them instead.
